# 加密货币量化交易平台 — 通用架构设计

> 本文是一份**通用**的技术设计参考：如果今天从零设计一个面向虚拟货币的量化交易平台，
> 推荐的架构、关键取舍与实现要点。它不描述本仓库的当前实现（那是 `PLAN.md` 的职责），
> 但两者共享同一套设计哲学，可互相印证。
>
> 每一章的写法是"给出推荐做法 + 说明为什么"，而不是罗列所有可能性。

---

## 1. 目标、范围与设计原则

### 1.1 能力闭环

一个完整的量化平台必须打通四段闭环，且**每一段的产出是下一段的输入**：

```
行情数据  →  研究与回测  →  模拟盘验证  →  实盘自动交易
（事实）     （假设检验）    （工程验证）     （真金白银）
```

- **行情数据**：历史 K 线 + 实时行情（tick / 订单簿），是一切的地基。数据不可靠，后面全部作废。
- **研究与回测**：在历史数据上检验策略假设，输出绩效指标与净值曲线。
- **模拟盘**：用实时行情 + 本地撮合跑真实策略代码，验证的是**工程正确性**（状态机、重连、风控），而非策略收益。
- **实盘**：对接交易所真实下单。此时新增的只应是 Broker 实现与安全护栏，策略与风控代码零改动。

### 1.2 定位与 Non-goals

设计之前先回答"给谁用、跑多快"。不同答案导向完全不同的架构，混着设计会两头不讨好。

**本设计的定位**：自托管、单人或小团队使用、中低频策略（秒级到分钟级决策）。

**明确不做（Non-goals）**：

| 不做 | 理由 |
|------|------|
| HFT 级微秒延迟 | 需要 colocation、内核旁路、定制网络栈，与自托管场景的成本完全不匹配；加密市场的中低频策略不靠延迟取胜 |
| 多租户 SaaS | 引入租户隔离、计费、合规审计等一整层复杂度，单人自用完全用不到 |
| 交易所级撮合引擎 | 我们只需要"回测/模拟用的简化撮合"，价格时间优先级队列等真实撮合语义没有必要复刻 |
| 去中心化交易所（DEX）| 链上交互（钱包、gas、MEV）是另一套技术栈，第一版聚焦 CEX |

### 1.3 三条核心设计原则

这三条原则贯穿全文，后续所有章节的具体设计都是它们的推论：

1. **回测与实盘共用同一份策略代码。**
   策略只依赖抽象的"数据输入 + 下单输出"接口，不感知自己跑在回测、模拟还是实盘。
   这是量化平台最重要的架构约束——否则"回测赚钱、实盘亏钱"中会永远混入一个无法排除的变量：两份实现不一致。

2. **一切有副作用的路径必须幂等且可审计。**
   下单请求可能超时后实际成功，进程可能在任意时刻崩溃重启。每个订单携带全局唯一的
   `clientOrderId`，重试用同一个 ID；每次状态迁移落库留痕。"不知道刚才那单发出去没有"是实盘最危险的状态，幂等键把它变成一次幂等的重查。

3. **交易所是不可信的外部系统，一切以对账为准。**
   WS 推送会丢、REST 会超时、余额会因为手工操作而变化。本地状态只是缓存，
   定期与交易所对账（余额、持仓、挂单），差异触发告警而不是静默覆盖。

## 2. 总体架构

### 2.1 模块分解

```
┌─────────────────────────────────────────────────────────────────────┐
│                          前端（React/TS SPA）                        │
│        行情看板 · 策略管理 · 回测工作台 · 交易面板 · 风控面板          │
└───────────────▲──────────────────────────────▲──────────────────────┘
        REST（配置/查询）                WebSocket（实时推送）
┌───────────────┴──────────────────────────────┴──────────────────────┐
│                        主服务（热路径，Go）                          │
│                                                                      │
│  ┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐  │
│  │ 行情网关    │──▶│ 策略引擎    │──▶│ 风控引擎    │──▶│ 交易执行OMS │  │
│  │ WS+REST    │   │ 实例生命周期 │   │ 事前/事中   │   │ 订单状态机  │  │
│  │ 重连/补缺   │   │ 事件分发    │   │ /事后      │   │ Broker路由 │   │
│  └─────┬──────┘   └────────────┘   └────────────┘   └─────┬──────┘  │
│        │                ▲                                  │         │
│        │          ┌─────┴──────┐   ┌────────────┐          │         │
│        │          │ 账务/对账   │◀──│  成交回报   │◀─────────┘         │
│        │          └────────────┘   └────────────┘                    │
└────────┼─────────────────────────────────────────────────┬──────────┘
         │              gRPC（仅回测时调用）                 │
         ▼                                                  ▼
┌──────────────────┐   ┌──────────────────┐   ┌─────────────────────┐
│   PostgreSQL     │   │ 回测工作服务       │   │  交易所（多家）       │
│ 全部业务表+K线    │   │ （Python，无状态） │   │  REST + WS          │
└──────────────────┘   └──────────────────┘   └─────────────────────┘
```

数据流两条主线：

- **行情流**：交易所 WS → 行情网关（清洗/统一符号）→ 策略引擎（事件）+ 前端推送 + 落库。
- **订单流**：策略产生意图 → 风控强制关卡 → OMS 路由到对应 Broker → 交易所 → 回报（WS 用户数据流）→ OMS 状态机 → 账务更新 + 策略 `on_fill` 回调 + 前端推送。

### 2.2 语言与进程边界

**推荐：热路径单进程静态语言（Go），研究/回测独立进程用 Python，gRPC 隔离。**

理由：

- **热路径要的是可靠而非生态**。行情断线重连、并发订单状态机、长时间不间断运行——Go 的并发原语、单二进制部署、可预测的内存行为都是为这类工作负载准备的。Rust 亦可，但在这个延迟档位（毫秒级可接受）Go 的开发效率优势更大。
- **研究要的是生态而非可靠**。pandas / numpy / backtrader / vectorbt 是十几年积累，用其它语言重造回测生态是最差的时间投资。回测崩了重跑即可，可靠性要求天然低一档。
- **进程隔离让两边互不拖累**。Python 的 GIL、依赖地狱、内存峰值都被关在回测进程里；回测服务无状态（数据由主服务通过 RPC 传入），可以随意水平扩展或崩溃重启。
- **契约收口到一个 proto 文件**。Go↔Python 的耦合面只有 gRPC 契约，两边独立演进。

### 2.3 单体优先，按"状态性"预留拆分线

**推荐：主服务先做成单体（modular monolith），但内部模块按未来可能的部署边界划分。**

微服务在这个场景是负资产：单人自用的流量撑不起服务治理的成本，而分布式带来的一致性问题（订单状态跨服务同步）恰恰是交易系统最不能承受的。

但拆分线要预留，且拆分依据是**状态性**而不是业务域：

| 模块 | 状态性 | 未来副本策略 |
|------|--------|--------------|
| 行情采集（交易所 WS） | 有状态（订阅会话） | 单例，多副本会重复订阅重复写库 |
| 策略引擎 + OMS | 有状态且有副作用 | **必须单例**（或分布式锁），多副本会重复下单 |
| Web API（查询为主） | 无状态 | 可多副本 |
| 回测 worker | 无状态 | 可多副本 + 自动扩缩，是水平扩展的最大价值点 |

## 3. 行情数据层

### 3.1 交易所适配器：REST + WS 双通道

每家交易所实现同一个数据源接口：

```go
type MarketDataSource interface {
    GetSymbols(ctx) ([]SymbolMeta, error)              // 交易对元数据（含精度规则）
    GetKlines(ctx, symbol, interval, from, to) ([]Kline, error)  // REST 拉历史
    SubscribeTicker(symbols, onTick) (stop func(), err error)     // WS 实时价
    SubscribeKline(symbols, interval, onBar) (stop, err)
    SubscribeDepth(symbols, onDelta) (stop, err)       // 订单簿增量（做市/套利需要）
}
```

**双通道各司其职**：REST 负责历史与缺口回补（可重试、有明确边界），WS 负责实时（低延迟、不可靠）。永远不要用轮询 REST 模拟实时，也不要指望 WS 补历史。

**断线重连是常态而非异常**：交易所 WS 会主动断开（Binance 24 小时强制断连）。适配器内置指数退避重连；重连成功后立即用 REST 回补断连窗口的 K 线缺口。缺口检测靠 K 线时间戳连续性：`open_time[n+1] == open_time[n] + interval`，不连续即补拉。

### 3.2 统一符号体系

**推荐：内部规范形式 `CRYPTO.BTC-USDT`，交易所原生形式（`BTCUSDT`、`BTC_USDT`）只存在于各自适配器内部。**

翻译层是**每所一个双向映射**，注册到路由表，而不是在一个函数里堆 if-else。规则只有一条红线：**原生符号绝不泄漏出适配器**——存储层、API 层、前端看到的永远是规范形式。加第二家交易所时如果发现原生符号散落各处，说明第一家就做错了。

前缀 `CRYPTO.` 看似冗余，是为未来多市场（股票 `CN.600519`）预留的命名空间，加前缀的成本是零，事后补前缀的成本是全量数据迁移。

### 3.3 三类数据的存储分层

| 数据 | 量级 | 存储 | 说明 |
|------|------|------|------|
| K 线（多周期） | 中 | PostgreSQL，`(symbol, interval, open_time)` 主键 | 幂等 upsert，天然去重；单机千万行内无压力 |
| 实时 tick | 大但不必持久 | 进程内缓存（最新值） | 前端快照与模拟撮合只需要"最新价"，历史 tick 除非做 tick 级回测否则不落库 |
| 订单簿 | 极大 | 进程内镜像，不落库 | 做市/套利策略消费实时镜像；回测用录制回放（单独文件存储）而非入库 |

PostgreSQL 单库起步，K 线量真正成为瓶颈时（数亿行、多年多所多周期）再上 TimescaleDB 插件——它与 PG 完全兼容，届时是加分区而不是换库，所以**现在不需要为它做任何事**。

**本地订单簿镜像**的标准维护算法（各大所语义一致）：先订阅 WS 增量并缓冲，再 REST 拉全量快照，丢弃 `updateId <= 快照 lastUpdateId` 的缓冲增量，之后逐条应用；一旦发现增量序号不连续，推倒重来（重新拉快照）。这个"快照 + 有序增量 + 断序重建"模式务必封装成通用组件，每家交易所只填差异参数。

### 3.4 限频治理

交易所限频（Binance 的 weight、Gate 的 req/s）是**账户级/IP 级全局资源**，必须集中管控：

- 每个交易所适配器内置一个令牌桶，该所的所有 REST 调用（行情回补、下单、对账查询）共享同一个桶。
- 桶的参数按交易所文档配置，留 20% 余量给突发。
- 命中 429/418 时指数退避，并触发告警——限频耗尽通常意味着某处代码在失控地重试。

限频逻辑放在适配器层而不是调用方，因为调用方（策略、对账、回补任务）彼此不知道对方的用量，只有适配器看得到全局。

## 4. 交易执行层（OMS）

### 4.1 可插拔 Broker

```go
type Broker interface {
    PlaceOrder(ctx, req PlaceOrderRequest) (*Order, error)
    CancelOrder(ctx, accountID, orderID) error
    ListOrders(ctx, accountID) ([]Order, error)
    GetPositions(ctx, accountID) ([]Position, error)
}
```

**模拟撮合（SimBroker）与真实交易所 Broker 实现同一接口**，上层（API、策略引擎、风控）通过账户配置路由到具体实现，完全不感知差异。这带来两个直接收益：

1. 策略从模拟切实盘是**改一个账户配置**，不是改代码；
2. 加一家交易所 = 实现一个接口 + 注册到路由表，其余层零改动。

SimBroker 的撮合规则刻意简化：限价单在最新价穿过委托价时全量成交，市价单按最新价立即成交，可配置滑点与手续费。不模拟排队与部分成交——模拟盘验证的是工程链路，撮合保真度是回测引擎（§7）的职责。

### 4.2 订单状态机：本地订单为主，回报驱动迁移

```
                    ┌──────────────┐
     提交成功        │              │ 全部成交
NEW ──────────▶ PARTIALLY_FILLED ──▶ FILLED
 │                   │
 │ 撤单/拒单          │ 撤单
 ▼                   ▼
CANCELED / REJECTED  CANCELED（可带部分成交）
```

关键设计：**订单的权威记录在本地库，状态只能由交易所回报驱动向前迁移**。

- 下单流程：本地先落一条 `NEW` 订单（拿到本地 ID 与 `clientOrderId`）→ 调交易所 → 记录交易所订单 ID。先落库再外呼，保证崩溃后能发现"悬而未决"的订单去交易所查证。
- 状态迁移只增不退：收到乱序回报（先 FILLED 后 PARTIALLY_FILLED）时丢弃旧状态。每条回报按 `(clientOrderId, 交易所序号)` 幂等去重。
- 成交（trade）与订单（order)分开记录：一个订单可有多笔成交，账务按成交流水计算，订单只是聚合视图。

### 4.3 实盘工程细节清单

这些细节每一条都对应一类真实事故，缺一不可：

| 事项 | 做法 | 不做的后果 |
|------|------|-----------|
| **幂等下单** | 每单生成唯一 `clientOrderId`，超时重试带同一 ID | 超时重试变成重复下单，双倍仓位 |
| **时钟同步** | 启动时与运行中定期校准交易所服务器时间，请求 timestamp 用校准值 | 本地时钟漂移几秒后所有签名请求被拒 |
| **精度校验** | 下单前按交易对元数据校验/修正 `tickSize`（价格步进）、`stepSize`（数量步进）、`minNotional`（最小名义额） | 策略算出 0.10000001 BTC 这类值被交易所拒单，策略却以为已挂上 |
| **用户数据流** | 订阅 WS user data stream 接收订单/余额实时回报；listenKey 定期续期 | 只靠轮询会漏掉快速的部成→全成序列 |
| **REST 兜底** | 每 30–60s 轮询未终态订单，与 WS 回报互为备份 | WS 静默断连期间订单状态永久卡住 |
| **密钥权限** | API key 只开"读 + 交易"，**禁提现**；主网与测试网 key 严格分开 | key 泄漏时资产被直接提走 |

## 5. 策略引擎

### 5.1 策略类型学

四类主流策略的事件模型与状态需求差异巨大，引擎设计必须先看清这张表：

| 类型 | 数据输入 | 决策频率 | 挂单模式 | 核心状态 |
|------|---------|---------|---------|---------|
| **CTA（趋势/信号）** | K 线（bar 级） | 每根 bar | 信号出现时市价/限价进出 | 指标窗口、当前持仓方向 |
| **网格** | 最新价 | 成交驱动 | 区间内密集双向限价单，成交一格补一格 | 网格线与每格挂单的映射 |
| **做市** | 订单簿（盘口） | 盘口每次变化 | 双边持续挂单 + 高频撤改 | 库存（净头寸）、在途挂单 |
| **跨所套利** | 两所最新价/盘口 | 价差穿阈值 | 两腿近同时下单 | 两腿的成交进度（单腿风险）|

结论：**引擎的事件接口必须同时支持 bar、tick、订单簿、成交回报四种驱动源**，且策略自己声明订阅哪些——给 CTA 推送每次盘口变化是纯浪费，给做市只推 K 线则根本没法做。

### 5.2 统一策略接口与生命周期

```go
type Strategy interface {
    Meta() StrategyMeta          // 类型、参数 schema、需要的数据订阅
    Init(ctx StrategyContext)    // 注入参数、账户、历史数据预热
    OnBar(bar Kline)
    OnTick(tick Tick)
    OnOrderBook(ob OrderBook)
    OnFill(fill Fill)            // 自己订单的成交回报
    OnTimer(t time.Time)         // 定时驱动（对账、网格重铺等）
    OnStop(reason string)        // 优雅停止：撤掉在途挂单
}
```

策略通过 `StrategyContext` 下单（`ctx.Buy/Sell/Cancel`），**永远不直接触碰 Broker**——上下文在中间插入风控关卡与订单归属标记（哪个策略实例下的哪些单）。

实例生命周期：`created → running → paused → stopped/errored`。

- `paused`：停止产生新订单，但保留在途挂单与状态（临时干预用）。
- `stopped`：撤掉全部在途挂单后退出（网格/做市尤其重要，遗留挂单等于裸敞口）。
- `errored`：策略回调 panic 时引擎捕获、隔离该实例并告警，**绝不能拖垮整个进程**——一个策略的 bug 不能停掉其他策略的交易。

### 5.3 参数 schema 自描述

策略在 `Meta()` 中导出参数元数据：

```json
{
  "type": "grid",
  "params": [
    {"name": "upper", "type": "float", "label": "区间上沿", "required": true},
    {"name": "lower", "type": "float", "label": "区间下沿", "required": true},
    {"name": "grids", "type": "int",   "label": "网格数",   "default": 20, "min": 2, "max": 200}
  ]
}
```

前端据此渲染**动态配置表单**，新增策略类型不需要改前端代码。同一份 schema 同时用于后端参数校验与回测参数网格搜索的空间定义——一处定义，三处消费。

### 5.4 状态持久化与崩溃恢复

**推荐：策略私有状态定期快照到库（JSONB），持仓与挂单不入快照、重启时从交易所对账重建。**

区分两类状态：

- **可从外部重建的**（持仓、在途挂单、余额）：交易所是唯一事实源，快照它们只会制造"快照与真实不一致"的新问题。重启流程 = 拉交易所挂单/持仓 → 与订单库比对 → 恢复归属关系。
- **只存在于策略内部的**（网格线映射、做市库存目标、信号窗口）：这些必须快照，丢了无法重建。成交回报处理完后同步落库，或按秒级定时快照（权衡：定时快照实现简单，代价是崩溃时丢最后几秒，恢复时靠对账补齐）。

## 6. 风控引擎

### 6.1 分层模型

```
事前（下单路径上，同步强制）    事中（持续监控，异步）        事后（成交/日终，异步）
├─ 交易未被 halt              ├─ 单币种集中度               ├─ 回撤熔断（净值跌破阈值→halt）
├─ 单笔名义额上限              ├─ 账户总仓位/总敞口           ├─ 异常成交检测（价格偏离告警）
├─ 资金/持仓充足               ├─ 跨所净敞口（套利单腿风险）   └─ 当日亏损限额
├─ 精度与最小名义额             └─ 挂单总量（做市撤改失败堆积）
└─ 单日下单次数上限
```

### 6.2 三条铁律

1. **风控是下单路径上的强制关卡，不是可选中间件。**
   `PlaceOrder` 的调用链固定为 `策略/手工 → 风控.Validate → Broker`，所有 Broker（模拟与实盘）共用同一个风控引擎。新规则加在风控引擎里，而不是散落在各 Broker 实现中——散落意味着新加一家交易所时规则会被遗漏。

2. **紧急停止（kill switch）必须独立于一切策略逻辑。**
   一个开关：halt 后拒绝所有新订单、可选撤掉全部在途挂单、可选全部平仓。它的触发路径要最短（一个 API、一个前端红按钮），因为用到它的时刻一定是最慌乱的时刻。

3. **实盘护栏默认最严，放松需要显式确认。**
   testnet 是默认环境；启用主网需要**两个独立的环境变量**（一个开关 + 一个人类可读的确认语句如 `I_UNDERSTAND_REAL_MONEY`），少一个都停留在测试网。API 密钥只从环境变量/Secret 注入，永不入库、永不出现在日志与 API 响应中。

风控事件（拒单、熔断、halt）全部落库（`risk_events` 表）并推送告警——被拒的单和成交的单同样值得审计。

## 7. 回测系统

### 7.1 双引擎：按策略类型路由

事件驱动与向量化回测的经典取舍在这里有一个更重要的前置问题：**不同策略类型需要的撮合保真度不同**。

- **CTA**：bar 级数据 + "下根 bar 开盘价成交"的简化假设已经足够，误差主要来自策略本身而非撮合。用成熟的 bar 级引擎（backtrader）最划算，其分析器（夏普、回撤、交易统计）都是现成的。
- **网格 / 做市 / 套利**：收益完全产生于**挂单被动成交**的微观过程。bar 级回测对它们无意义——一根 K 线内价格来回穿越多条网格线的次序、做市挂单是否排到队、两腿成交的时间差，这些 bar 级数据根本表达不了。它们需要 tick/订单簿级的事件回放 + 显式的成交概率模型。

**推荐架构：按策略类型路由到两个引擎。**

```
回测请求 ──▶ 按 strategy.type 路由
              ├─ CTA        → Python backtrader（bar 级，生态成熟）
              └─ 网格/做市/套利 → 自研事件回放引擎（tick 级，与实盘共用策略代码）
```

自研引擎写在热路径同一语言里还有一个额外收益：网格/做市/套利的策略实现**天然只有一份**，回测与实盘的一致性由编译器保证。CTA 是唯一需要维护两份实现（backtrader 版 + 实盘版）的类型，用"黄金数据回归测试"（同一段历史、两边跑、比对信号序列）控制漂移。

### 7.2 成本模型

回测收益里最容易造假的是成本。最低配置：

- **手续费**：maker/taker 分开配置（网格与做市几乎全是 maker，费率差异直接决定策略生死；有些所 maker 返佣，模型要支持负费率）。
- **滑点**：taker 单按固定 bp 或按盘口深度吃单模拟；后者需要订单簿数据。
- **成交概率（做市专属）**：挂单不是"价格触到就成交"。保守假设：价格**穿过**挂单价才算成交（touch ≠ fill）；进阶用排队位置估计。宁可保守——回测里多算成交等于虚增收益。
- **延迟**：信号产生到订单生效之间加固定延迟（如 100–500ms），对套利策略尤其关键，价差窗口常常比延迟还短。

### 7.3 参数优化与过拟合

- 支持参数网格搜索：参数空间由策略 schema（§5.3）定义，任务队列分发给无状态回测 worker 并行跑——这是回测服务可水平扩展的直接收益。
- **Walk-forward 验证**作为标准流程：滚动的"训练窗口调参 + 紧邻的验证窗口测试"，只看验证窗口的拼接绩效。
- 平台层面的防呆：报告中强制展示样本内/样本外的绩效对比；参数邻域敏感性（最优参数微调后绩效崩塌 = 过拟合红旗）。工具防不住所有过拟合，但至少让它显形。

## 8. 账务与对账

### 8.1 核心口径

- **成交流水是账务的唯一输入**。持仓 = 成交的累计；已实现盈亏在减仓成交时按加权均价结转；未实现盈亏 = 持仓 ×（最新价 − 均价），实时计算不落库。
- 账户净值 = 现金 + Σ(持仓 × 最新价)。净值曲线按分钟级采样落库，供绩效与回撤熔断（§6）使用。
- 手续费按成交记录，计入已实现盈亏——网格/做市这类薄利策略，忽略手续费的账是假账。

### 8.2 对账循环

**本地状态是缓存，交易所是事实源**（原则 3 的落地）：

- 定时（如每 5 分钟）+ 事件触发（重启、WS 重连后）执行对账：拉取交易所余额、持仓、挂单，与本地比对。
- **差异告警，不静默覆盖**。差异的常见来源：手工在交易所 App 下了单、WS 漏了回报、上一次崩溃留下悬单。每一种都值得人看一眼；自动覆盖会把 bug 的证据擦掉。
- 对账差异及其处理结果落库，形成审计线索。

## 9. 数据库核心 Schema

PostgreSQL 单库。核心表骨架（省略索引与约束细节）：

```sql
users            (id, username, password_hash, created_at)
symbols          (symbol PK, exchange, base, quote, status,
                  tick_size, step_size, min_notional)          -- 精度规则随元数据入库
klines           (symbol, interval, open_time, o, h, l, c, v, close_time,
                  PRIMARY KEY (symbol, interval, open_time))    -- 幂等 upsert
accounts         (id, name, kind /*sim|live*/, exchange, cash)
positions        (id, account_id, symbol, quantity, avg_price,
                  UNIQUE (account_id, symbol))
orders           (id, account_id, strategy_instance_id NULL, client_order_id UNIQUE,
                  exchange_order_id, symbol, side, type, price, quantity,
                  filled_qty, status, created_at, updated_at)
trades           (id, order_id, symbol, side, price, quantity, fee, traded_at)
strategies       (id, type /*cta|grid|mm|arb*/, name, params JSONB, schema_version)
strategy_instances (id, strategy_id, account_id, status, state JSONB /*快照*/,
                    started_at, stopped_at)
backtest_runs    (id, strategy_id, params JSONB, range, engine /*go|backtrader*/,
                  metrics JSONB, equity_curve JSONB, trades JSONB, created_at)
risk_events      (id, kind /*reject|halt|breaker|recon_diff*/, detail JSONB, created_at)
equity_snapshots (account_id, ts, equity, PRIMARY KEY (account_id, ts))
```

设计要点：

- `orders.client_order_id UNIQUE` 是幂等下单（§4.3）的数据库级兜底。
- `orders.strategy_instance_id` 可空：手工单与策略单同表，归属清晰，风控与审计不需要两套查询。
- 策略私有状态放 `strategy_instances.state JSONB`，不为每类策略建专表——策略类型会持续增加，schema 追不上。

**迁移策略**：迁移文件按序号追加、启动时自动执行、以迁移表记录幂等。**已发布的迁移永不修改**；改列名走"加新列 → 双写 → 切读 → 删旧列"的多迁移模式，保证任意版本可平滑升级。

## 10. Web API 与前端

### 10.1 API 设计

- **REST 负责配置与查询**：symbols/klines、策略 CRUD 与启停、回测提交与结果、订单/持仓/成交查询、风控状态与开关。
- **WebSocket 负责实时推送**：**单一连接、多消息类型**——`{type: "ticker"|"order"|"trade"|"risk"|"strategy", data: ...}`。前端按 type 分发。不要为每类数据开一条连接：连接管理、重连、认证都会乘倍。
- 推送走同一个 Hub（发布-订阅单例），后端任何模块要通知前端都是 `hub.Broadcast(type, payload)` 一行。

### 10.2 前端模块

| 页面 | 内容 | 要点 |
|------|------|------|
| 行情看板 | K 线图、自选列表、实时价 | K 线图库推荐 ECharts：K 线与绩效/组合图表一个库全包，少一套依赖 |
| 策略管理 | 实例列表、创建/启停、**动态参数表单** | 表单由策略 schema 驱动（§5.3），新策略零前端改动 |
| 回测工作台 | 配置、净值曲线、绩效指标、交易明细、参数寻优结果 | 样本内/外对比是一等公民 |
| 交易面板 | 账户切换（模拟/各所实盘）、订单/持仓/成交、手工下单 | 手工单同样过风控 |
| 风控面板 | 当前限额、风控事件流、**紧急停止大红按钮** | kill switch 触达路径最短 |

技术栈：React + TS + Vite；UI 库选定一套（如 Tailwind + shadcn/ui）后**不要混用两套**——半迁移状态比任何一套单独存在都糟糕。状态管理用轻量方案（Zustand）即可，交易面板的实时状态本质是 WS 推送的投影，重型状态库没有用武之地。

## 11. 安全

- **API 密钥**：只从环境变量 / K8s Secret 注入；权限最小化（读 + 现货交易，**禁提现**）；有条件时绑定出口 IP 白名单。密钥不入库、不进日志、不出现在任何 API 响应。
- **认证**：自托管单用户场景，用户名 + 密码（bcrypt 哈希入库）换 JWT 即可，不需要 OAuth/RBAC 的复杂度。但**必须有**——交易系统裸奔在局域网也是不可接受的，一个能下单的未鉴权端口等于把账户拱手让人。
- **审计日志**：登录、下单、撤单、风控开关、halt/unhalt、密钥相关配置变更，全部结构化落日志并可回查。
- **主网双确认**：见 §6.2 铁律三。

## 12. 部署与运维

### 12.1 容器化双轨

- **本地开发**：docker-compose 一键起全栈（PG + 主服务 + 回测服务 + 前端），源码挂载 + 热重载。
- **部署**：同一批镜像 + Helm chart 上 K8s。镜像构建：Go 多阶段 → distroless 单二进制；Python slim；前端静态产物 → nginx。
- 配置经环境变量注入（ConfigMap/Secret），代码零环境分支。

### 12.2 副本策略：交易系统的单例约束

再次强调 §2.3 的结论，因为它是交易系统上 K8s 最容易犯的错：

- **行情采集与交易执行必须单副本**（`replicas: 1` + `Recreate` 策略），或以分布式锁保证同一时刻只有一个实例在下单。盲目 HPA 的后果是重复订阅、重复下单——后者是真金白银的事故。
- **回测 worker 随意扩**，它是整个系统里唯一"越多越好"的组件。
- 主服务重启窗口内策略停止决策——比"两个实例同时决策"安全得多。配合 §5.4 的崩溃恢复，重启是分钟级的平滑操作。

### 12.3 监控与告警

自托管场景的务实配置：结构化日志（JSON）+ 少量核心指标 + 主动告警通道（Telegram/邮件/Server 酱）。

必须告警的事件：WS 断连超阈值、下单失败率突增、风控拒单/熔断触发、对账差异、回撤逼近熔断线、策略实例 errored。
**原则：任何"系统认为自己不健康"的时刻都要主动通知人**，因为自托管系统没有值班团队，告警就是唯一的值班员。

## 13. 演进路线建议

**推荐切法：每层复用前一层，风险后置。**

| 阶段 | 内容 | 验证目标 |
|------|------|---------|
| 1. 行情看板 | 单所数据接入、落库、前端 K 线 | 数据链路可靠（重连、补缺、去重） |
| 2. 回测 | bar 级引擎 + 一两个示例策略 + 绩效报告 | 研究闭环跑通 |
| 3. 模拟盘 | 本地撮合 + 订单状态机 + 风控 + 实时推送 | 工程正确性（状态机、幂等、恢复） |
| 4. 单所实盘 | 真实 Broker + 用户数据流 + 安全护栏 | 真金白银小额验证 |
| 5. 平台化 | 第二家交易所、策略引擎多类型、跨所风控、tick 级回测引擎 | 抽象层的成色（加一家所/一类策略的边际成本） |

顺序背后的逻辑：**前四步用最小的抽象成本打通闭环，第五步才为"多"付抽象税**。反过来（先设计完美抽象再实现）的失败模式是：抽象设计时没有真实的第二个实现做检验，等真接第二家交易所时发现抽象切错了位置，返工成本比"先具体后抽象"更高。

## 14. 关键取舍清单

| # | 取舍 | 结论 | 一句话理由 |
|---|------|------|-----------|
| 1 | 单体 vs 微服务 | 模块化单体，按状态性预留拆分线 | 自用流量撑不起服务治理成本，分布式一致性是交易系统最不能承受的复杂度 |
| 2 | 热路径语言 | Go（静态语言单进程） | 毫秒级延迟档位下，可靠性与并发原语比生态重要 |
| 3 | 回测生态 | 保留 Python（backtrader/pandas） | 重造回测生态是最差的时间投资 |
| 4 | 回测引擎形态 | 双引擎按策略类型路由 | CTA 用 bar 级足够；网格/做市/套利的收益产生在 bar 表达不了的微观结构里 |
| 5 | 撮合引擎 | 只做简化撮合，不复刻交易所语义 | 模拟盘验证工程而非收益，保真度是回测成本模型的职责 |
| 6 | 订单事实源 | 本地订单库为主，回报驱动 + 定期对账 | 交易所不可信，但本地也只是缓存——对账才是仲裁者 |
| 7 | 策略状态恢复 | 私有状态快照，持仓/挂单从交易所重建 | 可从外部重建的状态不快照，避免"快照与真实不一致"的新问题 |
| 8 | 符号体系 | 内部规范形式，原生符号锁死在适配器内 | 翻译层单点收口，多所扩展的边际成本才是常数 |
| 9 | 数据库 | PostgreSQL 单库，量大再加 TimescaleDB | 插件式演进路径存在，就不要提前付时序库的运维成本 |
| 10 | 实时推送 | 单 WS 连接多消息类型 + 单例 Hub | 连接管理、重连、认证的成本按连接数乘倍 |
| 11 | 风控位置 | 下单路径强制关卡，所有 Broker 共用 | 散落在 Broker 实现里的规则，在加新所时必然被遗漏 |
| 12 | K8s 副本 | 采集/交易单例，回测 worker 水平扩 | 重复下单是真金白银的事故；回测是唯一"越多越好"的组件 |
| 13 | 抽象时机 | 先单所打通闭环，接第二家所时再抽象 | 没有第二个实现检验的抽象，大概率切错位置 |
